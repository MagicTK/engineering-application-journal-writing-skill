# 通用方法与 Benchmark/Real-World 双案例论文

[English](../../skills/general-method-benchmark-realworld/SKILL.md)

套件版本：`4.2.28`

## 一、任务目标

构建方法为中心但工程主线清晰的论文：

- benchmark 支持已说明评价设置下的比较；
- real-world case 支持所测生产条件与任务下的工程相关性。

应说明每个案例检验什么，而不止列出两个数据集。benchmark 名称和真实产线来源本身不能证明实验受控、可重复或覆盖了多种运行变化。

## 二、适用判断

适用于：

- 方法希望超出单一产线或设备实例；
- 技术挑战可以独立于某一个站点表述；
- 有公开/受控 benchmark；
- 有真实工业数据或案例；
- 论文同时需要方法严谨性与应用相关性。

若贡献离不开一个具体生产机制或设备，应使用背景驱动 Skill。

## 三、定义适度通用的问题

用一段话说明：

1. 工程任务；
2. 反复出现的过程/数据属性；
3. 在该属性下仍需验证或改善什么能力；
4. 需要的设计原则；
5. 原则预期适用的工业范围。

问题应比一个数据集更广，但不能泛化为“所有工业数据”。

## 四、分离两组证据角色

| 证据角色 | Benchmark | Real-world |
|---|---|---|
| 可能目的 | 共同评价设置下的比较 | 所说明生产条件下的相关性 |
| 需要核实的优势 | 数据/设置可获得、标签来源、重复性及确实受控的因素 | 实测工艺背景与确实存在的变化 |
| 常见实验 | 主对比、消融、敏感性、鲁棒性、可视化 | 工艺描述、主对比、精选消融、工程解释 |
| 可支持结论 | 方法有效性 | 测试条件下的实际相关性 |
| 不能自动支持 | 部署 | 普适泛化或在线运行 |

除非回答工程问题，不机械重复所有 benchmark 实验。

## 五、论文主线

`反复出现的工业挑战 -> 当前建模假设局限 -> 通用设计原则 -> benchmark 证据 -> real-world 证据 -> 范围与边界`

每项贡献对应能够检验其实际主张的证据。通过[贡献论证路径](../../references/contribution-narratives.md)区分新问题、机制、工程适配和聚焦比较，按[论证与文字精修](../../references/argument-and-prose-craft.md)组织段落递进。

## 六、摘要与引言

摘要依次完成：挑战、已有能力与剩余要求、方法与原则、贡献必需的核心机制、两类案例、已核验结果及其工程意义。机制数量由实际贡献决定，不凑固定个数；结果若体现权衡或尚未得到确定结论，应如实表达。最后的证据句只需说明 benchmark 和 real-world case 及其支持的结论；除非类别不平衡、噪声或缺失本身就是核心问题，否则不在这一高层概述中罗列。采集的测量可以称 dataset，但要交代生产背景，不能用数据集名称代替适用性证据；没有实际运行证据时不推断部署。

引言可承担以下功能，不是必须写成八段：

1. 工程任务与重要性；
2. 反复出现的数据/过程属性；
3. 已有方法类别；
4. 与当前问题有关的假设局限；
5. motivation；
6. 论证确实需要的另一个不同表征要求；
7. 结构化方法响应；
8. 实际独立贡献；支撑操作归入其服务的贡献，不凑固定条数。

将真实案例连到证据安排，但开展案例本身不必列为贡献。合并重复功能；Related Work 融入引言时保留被引用的论证依据，不为每个模块另造一个挑战。

## 七、Related Work

围绕技术 gap 组织：工程任务方法、相关数据属性的建模、结构/知识/工况引导方法和必要的评价实践。由已有能力递进到本研究的剩余要求；有依据且能推进论证时才以局限或未覆盖的评价条件收束，否则承接该节的已有能力继续展开。未报告某项测试不能据此判定方法无能，不为每节制造批评，也不单独设一节罗列流行时序模型。

## 八、方法部分

每个实质组件按适用性说明下列要素；普通支撑操作只需明确作用，不重复写动机段落：

1. 反复出现的工程/数据问题；
2. 表征和操作；
3. 跨案例适用的原因；
4. 工序、拓扑、采样计划或知识等案例配置；
5. 固定设计与数据学习的边界。

不能把站点特定假设藏在“通用方法”中。

## 九、实验总览

开头说明 benchmark 在其数据、标签、划分和设置下进行什么比较，工业案例检验所测过程条件与任务下的什么适用性。随后介绍对比类别、共享设置、指标和公平性规则，再进入案例小节。

## 十、Benchmark 案例

包括过程/任务、变量与类别、划分、输入构造、主对比、贡献对应消融、核心参数敏感性、合理扰动鲁棒性，以及有科学问题的可视化。

在标签、重复性与受控因素确实适合的案例上安排相应机制分析，不从 benchmark 名称自动推断这些条件。

## 十一、真实工业案例

先说明：

- 实际过程、设备或生产路线；
- 变量与标签的工程含义；
- 样本单位与划分单位；
- 对案例有实质影响的噪声、缺失、类别频数差异和工况变化；
- 实际使用的领域知识；
- 主对比、精选消融与工程解释。

内部应明确证据来自回顾性生产记录、前瞻试验、影子运行还是在线系统，不同设置支持不同结论。只有离线/在线差异会影响方法解释或证据边界时，正文才需要使用 `offline`；其他情况下直接写 real-world industrial case、real-world production data 或实际生产过程。

类别不平衡按层披露：数据集小节给出类别数量，设置小节说明权重或采样，指标小节解释 macro/weighted/class-wise 指标，结果小节分析少数类别。除非处理类别不平衡本身就是研究问题或贡献，否则不在摘要、贡献、实验总览和结论中突出。

## 十二、对比方法

可采用：传统方法、标准深度学习、当前时序/模态方法、最相关的工业专用方法和本文方法。同一对比模型的名称与变体保持一致；任务或输入不同允许选择不同的合理对比集合，但应说明实质差异与实现条件。

## 十三、综合结果

不要写两个断开的结果摘要。回答：

1. benchmark 支持了哪个设计主张？
2. 真实案例是否显示同方向收益？
3. 哪些实际条件改变相对表现？
4. 哪些限制仍是案例特定？
5. 当前可支持何种泛化范围？

两个案例一致时可用 `consistent with`，不要从两个案例推出普适性。只讨论实质影响当前主张的未测条件；在线、跨站点和长期试验用于支持相应主张，不是每篇结尾必列的不足。

保留案例之间不同或相反的作用方向，据已记录的任务、数据和配置差别讨论，不凭案例名称臆测原因。两个案例分别重新训练同一种方法，不等于一个已训练模型跨案例迁移；目标、单位或分母不兼容的指标不能合成新的总分。按[讨论写法](../../references/section-writing-guide.md#15-discussion)把结果模式转化为有范围的工程解释。

## 十四、质量门

- 每组案例作用有依据，并明确共同证据与互补证据；
- 方法通用但不宣称普适；
- 真实案例已说明生产背景与任务，不以 dataset 名称代替工程依据；
- 对比公平；
- 表值与可视化标明运行及汇总范围，共用结果一致，合理差异有解释；
- practical applicability 未夸大为 deployment；
- 摘要与结论准确反映两种证据。
