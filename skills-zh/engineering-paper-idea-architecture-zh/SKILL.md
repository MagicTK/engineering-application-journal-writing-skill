# 工程应用论文选题与架构

套件版本：`4.1.36`

## 一、任务目标

在润色文字之前构建一篇完整论文：

`工程观察 -> 研究问题 -> 技术空白 -> 设计原则 -> 方法 -> 证据 -> 有边界的贡献`

研究可以由工程观察或方法洞察发起；贡献论证需要真实工业任务、明确建模要求与相应证据。

课题混合了挑战、方法、任务和对象层级时，先调用 [`industrial-ai-paper-router`](../industrial-ai-paper-router-zh/SKILL.md)，并只加载 [topic playbooks](../../references/topic-playbooks.md) 中被选中的主题。

工程观察或方法洞察都可以形成研究起点。进入贡献写作前，明确工业任务、尚未满足的要求以及该机制为何能够回应它；不能只从方法名称推出工程意义。

## 二、盘点材料

明确：

- 过程、设备、系统和决策目标；
- 变量、标签、采样、工序、单元、工况和知识来源；
- 已有方法、代码、图、结果与错误；
- benchmark 和真实工业数据；
- 目标期刊与篇幅；
- 作者希望保留的主张；
- 尚未确认的事实。

按 `verified`、`author-confirmed`、`inferred` 和 `missing` 标记。

## 三、选择论文范式

根据[论文范式](../../references/manuscript-archetypes.md)校准，不能只看模型名称。

### 通用方法 + 双案例

技术问题存在于多个过程，方法原则可通过有限配置迁移，并具备 benchmark 与真实工业证据。

### 真实工业背景驱动

一个过程、设备类、生产机制或运行流程产生问题并塑造方案。

### 工程系统/自动化框架

系统集成、接口、时序、决策流程、控制架构或部署行为是核心。

根据最强贡献和证据选择，不根据算法名选择。

## 四、形成研究问题

一个有效问题需要指出：

- 工程任务；
- 困难条件；
- 缺失能力；
- 适用范围。

不要只问“新网络能否提高准确率”。可使用主题中立模板：`在[已核实工业条件]下，针对[仍可改善的能力或假设边界]，如何在满足[运行或信息边界]的前提下可靠获得[工程输出]？` 每一处都必须来自当前课题事实，不能沿用校准论文中的观测、依赖、频率或监督主题。

## 五、区分创新类型

- **问题定义创新**：更忠实地表示实际条件；
- **方法原则创新**：提出回应条件的新机制；
- **工程集成创新**：连接传感、知识、模型和决策；
- **证据创新**：可信地评价困难工业任务或能力；
- **系统创新**：验证接口、流程、时序或自动化行为。

明确主创新及有证据支撑的辅助创新，不把每一类都写成“主要贡献”，也不强制固定条数。

暂定贡献路径：A机制研究、B实质工程适配、C聚焦增量改进。它们不是期刊分区或录用预测。允许有引用的任务、数据和基线代码复用；独立研究需要实质增量与对应证据。详见[贡献边界](../../references/research-planning-and-contribution.md)与[跨论文差异表](../../assets/templates/cross-paper-delta.md)。

Gap可以是既有条件下仍可改善的能力，不强迫提出新问题或宣称所有旧假设失效。借鉴模块与本次修改分别说明。

### 选择贡献论证路径

按[贡献论证路径](../../references/contribution-narratives.md)选择主线：新问题建模、熟悉问题的新机制、约束相互作用、工程适配或聚焦比较；它与论文范式是不同维度。准确交代已有成果，指出具体条件下仍未满足的要求，把本次机制连到能区分其作用的实验。方法更强不必意味着问题更新，新问题也不强制新机制。泛化或工程收益先设计匹配验证，再依据实际结果表述。

## 六、建立 Problem-Design-Evidence Blueprint

| 工程/数据挑战 | 仍可改善的能力或假设边界 | 设计响应 | 所需证据 | 边界 |
|---|---|---|---|---|

每个主要模块说明作用，每个主要主张有匹配证据。用合适的比较、分析或干预检验声称的增量；删除耦合组件不一定构成有效的隔离消融。标准支撑组件说明来源与必要性，无需虚构独立创新点。缺少合理作用的组件先交作者讨论，不能在文字修改时直接删除。

## 七、形成内部主旨句

采用：

> 对于[具体条件]下的[工程任务]，[设计原则]实现了[能力]，并通过[证据范围]进行验证。

这不是必须写入论文的原句，而是架构检查工具。无法准确写出时，不应进入全文写作。

## 八、先设计证据

逐项决定主张需要：

- 对比；
- 消融；
- 鲁棒性/工况变化；
- 敏感性；
- 可视化或解释；
- 效率/时序；
- 真实案例；
- 专家/工艺一致性；
- 统计不确定性。

没有实验时，不承诺泛化、鲁棒、可解释、轻量化或部署。

## 九、规划图的科学作用

常见作用：过程背景、motivation、整体框架、关键模块、实验流程、结果问题、工程案例解释。总览图与提供必要操作或信息流的模块详图可以互补；仅在作者同意后删除冗余，文字审查不授权重画已确认框架。

## 十、章节架构

### 方法型

`Introduction -> Related Work -> Problem/Motivation -> Method -> Benchmark -> Real-world case -> Discussion -> Conclusion`

### 背景驱动型

`Introduction -> Process/System and Evidence -> Method -> Industrial Experiments -> Engineering Discussion -> Conclusion`

### 系统型

`Introduction -> Requirements -> Architecture -> Implementation -> Evaluation -> Discussion -> Conclusion`

这些是可能的逻辑结构，不是强制章标题。保留引用论证的前提下，可将 Related Work 融入 Introduction，或合并 Motivation and Problem Formulation。根据已核实的期刊要求调整，不为形式对称增加章节。

## 十一、把贡献写成合同

一条主贡献和必要的支撑贡献，不凑固定数量；每点包含对象、机制、intended effect 和必要证据。方法和实验必须履行贡献项，不得把摘要换一种说法再列一遍。

## 十二、对抗性检查

1. 工业背景是否帮助理解任务、信息约束或评价？通用方法可以跨场景保持不变，不能仅据此认定工程应用表面化。
2. 每个模块是否具有合理作用？标准预处理或预测组件可以必不可少，但无需各自成为创新点。
3. 最强主张是否依赖缺失或很弱的实验？
4. 是否把站点特定假设藏在通用主张中？
5. 真实案例是否改变科学结论，还是只作展示？

## 十三、预期产物

- 论文范式及理由；
- 一句话主旨；
- 研究问题与范围；
- 创新层级；
- Problem-Design-Evidence Blueprint；
- 章节与段落功能；
- 图表作用；
- 实验需求；
- 简短的作者决策清单。

## 十四、质量门

问题应有独立于所选模型的依据，设计应回应所述问题，但不虚构研究在历史上如何由工程问题推导而来。主张应匹配证据，真实案例应有明确角色，创新应具体有边界，模型术语应在工程对象定义后出现，缺失事实不得被虚构。
